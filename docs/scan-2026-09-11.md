# Non-Web3 OSS target scan — 11 Sep 2026

Decision log for the next contribution batch, tuned for the stated preference: **tier-2 / tier-3 reputable non-web3 repos**, because tier-1 queues are too competitive for this account (AgentScan auto-closes, maintainer-reserved work, first-timer CI gates).

**Cut-off:** 11 Sep 2026, ~19:00 UTC. Every row below was live-verified on 11 Sep 2026: state, assignee, comment thread scan for claims, and timeline cross-references for competing PRs. GitHub state changes fast; re-check the issue timeline immediately before claiming.

**Tier labels:** **T2** = established mid-size repo (roughly 2k-30k stars, real maintainer team, steady releases). **T3** = smaller but reputable (hundreds to ~2k stars, notable maintainer, real usage).

**Method note:** bulk issue discovery ran through the core `repos/{owner}/{repo}/issues?labels=bug` endpoint instead of the search API. The search endpoint trips its secondary rate limit after ~2 rapid calls; the core endpoint does not. Competing-PR detection used per-issue timeline `cross-referenced` events. Foreign-repo cross-references can 404 when resolved as PRs; a 404 is treated as a foreign reference, not an open competitor.

Item 4 (crawlee#2815) was worked on 12 Sep 2026 and is still GO but rescaled. Verified on current `main`: `serializeValue` in `packages/core/src/storages/key_value_store_codec.ts` still rethrows `Object is too large` for oversized objects, and `jsonStringifyExtended` is a plain `JSON.stringify` wrapper with no large-object handling. Prior PR [#2925](https://github.com/apify/crawlee/pull/2925) died stale, but member `barjin`'s review is a usable spec: vitest only, dependency in `packages/core/package.json`, preserve binary-type passthrough, and do not blanket-catch stringify errors (only the `Invalid string length` RangeError). That needs an approach comment first (comment approval gate) before coding.

Item 5 (msw#2748) was redirected the same day: in the msw repo the member `kettanaito` has already gated it ("React Native not having a public `.body` property on the `Response` is a huge violation of the spec... this isn't something MSW can/should address"). Verified present on interceptors `master`. No open issue or PR tracks it in interceptors. Vehicle: a new issue there proposing either pass-through of the raw Response when no decompression applies and `.body` is missing (pre-0.41.7 behavior), or a loud error instead of a silent empty body. Needs the maintainer's design choice first (approach comment, comment approval gate).

## Learned patterns for this account (verify each time)

- **Fresh bug clusters race fast.** typeorm and sqlalchemy issues from August-September 2026 each had open PRs before any triage label. A 0-comment issue is not a clear field - always timeline-check cross-referenced PRs even at 0 comments.
- **Companion repos matter.** fastapi-users#1296 looked GO but the fix belongs in `fastapi-users-db-sqlalchemy`. Before claiming a library issue, confirm which package actually owns the code.
- **Closed-unmerged prior attempts** on an unassigned issue usually mean an approach mismatch, not an abandoned bug. Read the close reason and both diffs before re-attempting.
- **Maintainer actively re-testing with the reporter** = hands off until triage concludes (nock#2919, crawlee#3182).
- **Core-API scanning beats search-API scanning** for bulk sweeps: `repos/{}/issues?labels=bug` + per-issue `timeline` avoids the search endpoint's secondary rate limit entirely.

## Pre-flight checklist (per target, before claiming)

- [ ] Refresh issue state, assignees, comments, and cross-referenced PRs via the core API.
- [ ] Re-read the repo's contribution and AI-assistance policy.
- [ ] Reproduce on the current default branch.
- [ ] Post a concise, human-reviewed claim/approach comment only where etiquette calls for it (comment approval gate applies).
- [ ] Keep the patch bounded; add a failing-first regression where tests exist.
- [ ] Never compete with a PR that appears after this scan.
